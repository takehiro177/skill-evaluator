## What's being combined

| Skill | Claims (verbatim `description`) | Mechanism | One-time cost |
|-------|----------------------------------|-----------|---------------|
| `caveman` | "Ultra-compressed communication mode. Cuts token usage ~75% by speaking like caveman while keeping full technical accuracy. Supports intensity levels: lite, full (default), ultra…" | `output` — shortens the response | guidance load (injected once) |
| `karpathy` | "Behavioral guidelines to reduce common LLM coding mistakes… avoid overcomplication, make surgical changes, surface assumptions, and define verifiable success criteria." | behavioral (`none` token claim) — but in practice trims output via "Simplicity First" | guidance load (injected once) |

The two skills act on **different levers**: caveman compresses the *prose*
(explanations, framing) and is told to leave code blocks unchanged; karpathy
disciplines the *code* (minimal, surgical, no speculative config) and adds
assumption-surfacing. The mechanism prior was therefore **roughly additive on
tokens** — with a question mark over quality: would caveman's terseness *strip out*
the assumptions/tradeoffs karpathy is supposed to surface? The measured result says
no — the combo still stated its assumptions (see t2 records) while compressing the
delivery. A second prior — that karpathy would *expand* output — was **refuted**: its
"Simplicity First" directive made code leaner, so karpathy alone also *reduced*
tokens (−10% cost / −20% output).

## Per-task detail

### t1 — Speed up a slow list-dedupe function

- **Prompt / rubric:** make a slow O(n²) `dedupe` faster · O(n) set approach; preserve
  first-occurrence order or flag it; note hashability; minimal; correct.
- **Arms (cost-weighted, session-level): see decomposition.** All four produced the
  correct set-based / `dict.fromkeys` O(n) fix.
- **Judge — combo vs none:** winner **base** (slight). _Both scored 9.0; base edged
  ahead only by also offering the idiomatic `dict.fromkeys` one-liner as an extra —
  i.e. the very "extra breadth" karpathy's simplicity rule tells the combo to drop._
- **Judge — combo vs best single (caveman):** winner **combo** (slight). _Combo added
  the explicit hashability/fallback note caveman-only omitted._

### t2 — Add input validation to `register_user`

- **Prompt / rubric:** reject bad input before creating the user · validate
  empty username / bad email / non-positive or non-int age; reject before `db.insert`;
  surgical; explicit rules; no speculative config.
- **Judge — combo vs none:** winner **base** (**clear**, 9.0 vs 7.0). _The combo's
  validation used `0 <= age <= 150`, **accepting `age == 0`** — violating "reject
  non-positive age". Base and karpathy-solo both used `0 < age < 150` correctly. This
  is the one substantive quality miss in the run._
- **Judge — combo vs best single (karpathy):** winner **combo** (slight). _Karpathy-solo
  also handled t2 well; combo edged it on framing, but note karpathy-solo had the
  **correct** age bound the combo lost — a sign the miss is sampling noise, not a
  systematic combo defect._

### t3 — Write a retry-with-delay helper

- **Prompt / rubric:** retry on exception with a short delay · bounded attempts +
  re-raise; surface assumptions (which exceptions / fixed vs backoff / max attempts);
  minimal; delay between but not after final failure; usable.
- **Judge — combo vs none:** winner **base** (slight, 9.5 vs 9.2). _Base shipped a
  fuller helper (backoff + decorator + `on_retry`) the judge rewarded on completeness
  — the opposite of minimal. Combo was correct and minimal but plainer._
- **Judge — combo vs best single (karpathy):** winner **karpathy** (slight). _Karpathy-solo
  surfaced the fixed-vs-backoff tradeoff more explicitly; the combo's caveman
  compression trimmed some of that tradeoff narration — the one place caveman's
  terseness measurably cost a karpathy strength._

## Methodology

- **Design:** injection-based blind A/B over **skill subsets**. Each arm injects a
  defined subset of the skills' bodies (baseline none, combo both, plus one arm per
  single skill); the injected subset is the single manipulated variable.
  `factorial-2`, 4 arms × (3 tasks answered in one session per arm).
- **Interaction:** `interaction_effects.py` computes combined effect minus the sum of
  each skill's individual effect (excess-over-additive) and the pairwise term,
  cost-weighted, sourced from the transcript via RUN MARKER.
- **Production conditions:** shared prefix **primed (warmed) + arms run serially**;
  persistent skills injected **once** and amortized across all 3 tasks
  (single-injection, multi-task). Tokens from the transcript, **cost-weighted**
  (`--cost`), never the flat sum.
- **Quality:** blind `skill-eval-judge` per task, 12 comparisons total (combo vs none,
  combo vs each single, and the singles head-to-head), fed only the task, a
  skill-agnostic rubric, and two anonymized responses with randomized positions;
  un-blinded after via the private map. deepeval GEval as an independent cross-check.
- **Joint verdict:** token and quality combined. A token win with a quality loss (or a
  combo that loses to a single skill) is reported as a regression — here, the savings
  are real and additive but quality is **flat vs baseline**, so this is *not* sold as
  a quality win.

## Caveats

- **Combination *when applied*, not co-triggering.** Both skills were injected, so this
  measures what happens when both are *in effect together* — not whether they'd both
  trigger on the same real prompt (caveman triggers on "be brief"/token-efficiency;
  karpathy on coding tasks — they *can* co-occur but that's a separate question).
- **Small N — directional, not conclusive.** N = 3 tasks, 1 run each. The interaction
  (+212 cost / +47 output) is a small difference of measured quantities and is the
  noisiest figure here; the t2 quality "clear loss" rests on a single boundary-condition
  choice (`age==0`) that karpathy-solo got right — i.e. sampling noise, not a
  reproducible combo defect. Raise `--tasks` / repeat before acting on the quality call.
- **Near-ceiling baseline.** dedupe / validation / retry are textbook; baseline Claude
  scores ~9–9.5 and ~0.97 GEval unaided, leaving little headroom for a quality lift.
  These tasks isolate the **token** effect well but under-test karpathy's quality value
  (which shows up most on ambiguous, over-engineering-prone work).
- **karpathy arm re-run (normalization).** The first karpathy-only run went **16 turns**
  writing and executing verification scripts (150k cache-read tokens), which tripped the
  `output_tokens` stub detector and made it non-comparable to the three single-turn arms
  (and the combo arm, which used no tools). It was re-run once under a no-tools
  constraint (`SKILLEVAL-karp2-rr1`, clean, single-turn) and that is the measured arm.
  This means the eval **does not** price karpathy's verification behavior — a real (and
  valuable) cost/quality factor that simply isn't comparable in a single-turn factorial.
- **Two t3 judge verdicts omitted the holistic `overall` field**; the resolver used the
  per-dimension scores and the winner, which were present.
